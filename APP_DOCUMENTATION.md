## 1. What the app is

A multi-tenant **HR / attendance app** (Flutter client) on top of one Firebase project (`attendence-a56dd`, Firestore location `nam5`). It shares its Firestore database with a separate **Workzi web app**; many field names and the double-write patterns exist only so the web app and the mobile app can read each other's data.

Main features: GPS geofenced check-in/out, leave requests and approvals, attendance correction requests, tasks, announcements, team feed, documents, company policies, departments/employees, calendar, reports, push notifications.

Platforms configured: Android, iOS, Web, macOS, Windows (`firebase_options.dart`), plus Linux boilerplate.

## 4. Boot, login and session flow

1. `main()` → `Firebase.initializeApp` → register FCM background handler → `NotificationService().initialize()` → `runApp(AttendanceApp)`.
2. `home:` is `AuthWrapper` ([auth_wrapper.dart](lib/screens/auth_wrapper.dart)). It listens to `FirebaseAuth.authStateChanges()`.
   - Signed out → `LoginScreen`.
   - Signed in → load session (below) → check GPS permission → `UnifiedDashboardScreen`.
3. **Session loading** — how the app finds which company a user belongs to:
   1. Read `approved_users/{email}` → gets `role`, `orgId`/`companyId`.
   2. If found → `_loadSessionFromOrganizations`: read `organizations/{orgId}`, then `organizations/{orgId}/members/{uid}` for name/department/shift, falling back to `organizations/{orgId}/users/{email}`, then to `adminDetails` on the org doc.
   3. If **not** in `approved_users`, fallbacks (and auto-creates an `approved_users` doc when one succeeds):
      - org where `managerEmail == email` → role `manager`
      - org where `adminDetails.email`, `superAdminEmail` or `contactEmail == email` → role `hr_admin`
      - `collectionGroup('users').where('email' == email)` → takes company and role from that user doc
   4. Fetch the applicable **shift** (`organizations/{cid}/shifts`) — by user's `shiftId`, else matching department, else `"All"`, else the first shift.
   5. `AppSession.populate(...)`, `updateOfficeLocationFromMap(orgDoc)`, `NotificationService.onUserLogin()`.
   6. Live listeners are attached to the org doc (permissions, geofence flag, office location) and to the `shifts` collection, so web-app changes apply immediately.
4. If location service or permission is off → `LocationRequiredScreen` blocks the app.

**Important:** the old docs mention `AdminDashboardScreen`, `ManagerMainScreen`, `EmployeeMainScreen`. **These classes do not exist.** All three roles land on the single `UnifiedDashboardScreen` ([unified_dashboard_screen.dart](lib/screens/unified_dashboard_screen.dart), 4,574 lines), which shows or hides tabs based on permissions.

## 5. Roles and the permission matrix

Roles stored in Firestore are normalised in the app to three: **`hr_admin`** (legacy `admin`, `super_admin`, `superadmin`, `hradmin` all map to it), **`manager`**, **`employee`**.

`AppSession.hasPermission(key)` rules:
1. `geofencing` is checked first, for every role, including HR Admin: org flag `isGeofencingEnabled` must be true **and** the role's list must contain `geofencing`.
2. HR Admin → everything else is `true`.
3. "Baseline" keys are always `true` for everyone: `my-space, dashboard, attendance, leave, tasks, documents, team, calendar, announcements-view, announcements, reports, settings, support, history, notifications`.
4. Action keys are resolved through aliases and checked against `organizations/{cid}.featurePermissions[role]`:

| Canonical key | Aliases | Default for manager | Default for employee |
|---|---|---|---|
| `approval` | approvals, approve-leave, approve-attendance, dashboard-approval, team-approval | yes | no |
| `task_creation` | task-creation, create-task, task_create | yes | no |
| `announcement_creation` | announcement-creation, create-announcement | yes | no |
| `organization` | org, organization_management | no | no |
| `geofencing` | geofence, geo-fencing | yes | yes |

`featurePermissions` is a map on the organization doc: `{ "manager": ["approval","geofencing"], "employee": [] }`. It is edited by the web app; the mobile app only reads it.

## 7. Firestore — where everything is stored

### 7.1 Big picture

```
(root)
├─ approved_users/{email}                      ← global login → company mapping
├─ organization_setup_requests/{id}            ← (rules only; no live code uses it)
├─ admin_users/{uid}                           ← platform super-admins (rules only)
└─ organizations/{companyId}                   ← THE tenant. Everything else lives under it.
   │
   ├─ [org doc fields]  settings, geofence, shift defaults, featurePermissions …
   │
   ├─ users/{email}                            ← employee profiles (doc id = lowercase email)
   │   ├─ attendance/{yyyy-MM-dd}              ← one doc per day
   │   ├─ leave_requests/{reqId}
   │   ├─ notifications/{id}   (+ docs "settings", "privacy", "security")
   │   └─ overtime_requests/{id}
   │
   ├─ members/{uid}                            ← web-registered org members (read for name/dept)
   ├─ shifts/{shiftId}
   ├─ attendance/{email}_{yyyy-MM-dd}          ← company roll-up mirror of the daily record
   ├─ leave_requests/{reqId}                   ← company-level leave queue
   ├─ attendance_issues/{id}                   ← attendance correction requests
   ├─ shift_requests/{id}                      ← read only by the Approvals screen
   ├─ department_requests/{id}                 ← read only by the Approvals screen
   ├─ task_requests/{id}                       ← read only by the Approvals screen
   ├─ tasks/{taskId}
   ├─ announcements/{id}  (+ comments/{id})    ← audience = everyone
   ├─ team_announcements/{id}                  ← audience = specific teams
   ├─ team_feed/{postId}
   ├─ global_notifications/{id}                ← company-wide / manager alerts
   ├─ policies/{id}
   ├─ documents/{docId}
   ├─ holidays/{id}
   ├─ support_tickets/{id}
   └─ company_calendar/{yyyy-MM-dd}            ← only dead code touches it
```

**Tenant isolation** is by path (`organizations/{companyId}/…`) plus the in-app guard `FirestoreService.isDocInCurrentCompany`, which also checks a `companyId`/`orgId`/`organizationId` field if present. Almost every document the app writes also stores a `companyId` field.

### 7.2 Top-level collections

#### `approved_users/{email}` — doc id = lowercase email
Global map from an email to a company and role. Read at every login.
| Field | Type | Notes |
|---|---|---|
| `email` | string | |
| `role` | string | `hr_admin` / `manager` / `employee` (legacy values accepted) |
| `companyId`, `orgId` | string | same value, both written |
| `status` | string | `approved` |
| `createdAt` / `approvedAt` | timestamp | |

*Written by:* `add_employee_screen` (batch with the user doc), `auth_wrapper` (auto-provision for managers/admins found by fallback).
*Deleted by:* `employee_detail_screen` (dead code).
*Read by:* login, `notification_helper` (query by `companyId` + `role` to find managers/admins), `manager_notifications_screen`.

#### `organization_setup_requests/{id}`
Pre-login "register your company" form. Rules require fields `flow="pre_login_organization_setup"`, `status="pending_admin_setup"`, `workspaceStatus="active"`, `organizationName`, `contactPerson`, `contactNumber`, `contactEmail`, `addressLine1`, `city`, `state`, `country`, `postalCode`, `timeZone`, `organizationType`, `organizationSize`.
**No live code reads or writes it** — the helper exists in `firestore_service.dart` but the registration screens are dead. It is almost certainly written by the web app.

#### `admin_users/{uid}`
Platform super-admin marker. Only the security rules reference it (`isAdmin()` = a doc exists here for the caller's uid). Not touched by the Flutter code.

### 7.3 `organizations/{companyId}` — the company document
Fields the mobile app **reads** (written by the web app unless noted):
| Field | Meaning |
|---|---|
| `companyName` / `name` | display name |
| `managerEmail`, `superAdminEmail`, `contactEmail`, `adminDetails{email,name,…}` | used for login fallback and for rules |

### 7.5 `organizations/{cid}/users/{email}/attendance/{yyyy-MM-dd}` — daily attendance
Written by `FirestoreService.recordAttendancePunch` (check-in and check-out merge into the same doc) **and mirrored** to `organizations/{cid}/attendance/{email}_{yyyy-MM-dd}`.
| Field | Example / notes |
|---|---|
| `companyId`, `userId`, `email`, `workEmail`, `employeeId` | all hold the employee email |
| `name` | employee name |
| `status` | `Present` / `Late` / `WFH` / `Half Day` (set at check-in) |
| `isLate` | bool, computed from shift start + grace |
| `shiftId`, `shiftName`, `shiftStartTime`, `shiftEndTime`, `gracePeriod` | snapshot of the shift used |
| `date` | string `yyyy-MM-dd` (web-app format) |
| `dateTimestamp` | Timestamp of midnight (for range queries) |
| `recordDate` | string `yyyy-MM-dd` |
| `checkIn` (Timestamp), `checkInTime` ("hh:mm a"), `checkInTimestamp` (ISO string), `checkInLocation` | |
| `checkOut`, `checkOutTime`, `checkOutTimestamp`, `checkOutLocation` | set on check-out |
| `attendanceStatus` | `Checked Out` after check-out |
| `hoursWorked` ("7h 30m"), `hoursNum` (number) | computed at check-out |
| `location` | address string, or "Work from Home" / "Work in Office" |
| `updatedAt` | ISO string |
| Adjustment fields (written by review screens): `isAdjustmentRequest`, `remarkStatus` (`pending/approved/rejected`), `adjustedCheckIn`, `reviewNote`, `reviewedAt`, `userName`, `isCorrection` | |

Date/time is stored in **several redundant formats on purpose** (Timestamp, ISO string, display string) because the web app expects strings and the mobile UI historically expected Timestamps. The correction-approval helper writes `date` as a `Timestamp` on the user doc but as a string on the roll-up doc — the same field name with two types.

### 7.6 `organizations/{cid}/attendance/{email}_{date}` — company roll-up
Identical payload to 7.5. Used for company-wide queries (reports, admin attendance, calendar) without needing a collection-group query.

### 7.7 Leave requests — **two copies**
`FirestoreService.submitLeaveRequest` writes the **same payload** to:
1. `organizations/{cid}/leave_requests/{reqId}` (company queue, what managers read)
2. `organizations/{cid}/users/{email}/leave_requests/{reqId}` (employee's own list)

`reqId` is `LR_<millisecondsSinceEpoch>`.
| Field | Notes |
|---|---|
| `id`, `companyId`, `userId` (auth uid) | |
| `applicantEmail`, `userEmail`, `employeeEmail`, `applicantName`, `userName` | same person under several names |
| `type` / `leaveType` | e.g. "Annual Leave", "Sick Leave", "Casual Leave" |
| `from`, `to` | strings `yyyy-MM-dd` |
| `fromDate`, `toDate` | Timestamps |
| `days` / `durationInDays` | int |
| `reason` | |
| `status` | **`Pending`** (capital P) at creation |
| `applied` | "MMM dd" |
| `createdAt` | ISO string |
| `targetRoles` | `["manager","hr_admin"]` (or just `["hr_admin"]` if requester is manager/admin) |
| `approver` | "Reporting Manager" or "HR Admin" |
| on review: `status` (`approved`/`rejected` — **lowercase**), `reviewedAt`, `reviewComment`, `approvedBy` | |

> ⚠ Status casing is inconsistent (`Pending` vs `approved`). Some screens compare with `.toLowerCase()`, others with an exact string. See section 13. Also, an approval updates only the doc it was opened from; the other copy is not updated by `leave_approval_screen` (see 13).

| Field | Notes |
|---|---|
| `userId` | employee email |
| `attendanceDate` | Timestamp of the day to fix |
| `correctedCheckIn`, `correctedCheckOut` | "HH:mm" strings |
| `reason` | |

## 8. Firestore security rules

Summary of `firestore.rules` (777 lines):

- **Helpers:** `isSignedIn`, `isAdmin` (doc exists in `admin_users/{uid}`), `userCompanyId` / `isManager` (read `approved_users/{email}`), `isOwner(email)` (token email equals doc id), `isOrgAdmin`, `isOrgMember`, `isOrgManager` (several ways to qualify: `approved_users` mapping, an `organizations/{id}/users/{email}` doc, `members/{uid}`, org-doc email fields, or the org id equal to caller uid).
- `approved_users`: owner / managers of same company / admin can read; managers and org admins can create/update/delete for their company.
- `organizations/{orgId}`: members and the org's contact emails can read; `isOrgManager` update; anyone signed in can **create** an org doc.
- Under an org, explicit rules exist for: `members, departments, designations, shifts, policies, locations, branches, leave_types, holidays` (members read / managers write), `users` and its `attendance, leave_requests, notifications, overtime_requests, notification_meta`, `global_notifications, attendance, leave_requests, announcements, tasks, documents, support_tickets, audit_logs, settings, notifications, attendance_issues, team_announcements, team_feed, outgoing_emails`.
- Everything else under an org is **admin only** (`/{allSubcollections=**}`) and, at root, `/{document=**}` is admin only (default deny for normal users).
- Legacy blocks still present: `approved_companies/**`, `companies`, `users`, `user`, root-level `notifications`, `leave_requests`, `overtime_requests`, `company_users`, `mail`, plus wildcard collection-group rules for `records`, `attendance`, `leave_requests`, `attendance_corrections`, `tasks`, `users`. **The app does not use any of those paths** (it uses `organizations/{cid}/…`).

Other rule/behaviour mismatches to check:
- `announcements` write is `isOrgManager` only, but `announcement_detail_screen` (live) updates the announcement doc, and the old employee tabs "liked" announcements via a transaction update. Any such update by a non-manager would be denied.

- `audit_logs` and top-level `audit_logs` are readable/writable by any signed-in user.

## 9. Firestore indexes (`firestore.indexes.json`)

12 composite indexes and 8 field overrides, all for **paths the live app does not query**:
- `records` (legacy `attendance/{uid}/records`): 6 composite + field overrides.
- `attendance` collection-group: `companyId+date`, `companyId+isAdjustmentRequest+remarkStatus`, plus `companyId` override.
- `leave_requests`: `userId+status`, `companyId+status` (collection-group).
- `announcements`: `status+timestamp`.
- field overrides enabling collection-group queries on `companyId` for `tasks, leave_requests, attendance, overtime_requests, notifications, records`.

Live code almost always uses `.snapshots()` / `.get()` on a whole collection and filters in memory, so it needs **no** composite indexes. The only filtered queries are `where('status'=='approved')` on users, `where('email'==…)`, `where('role'…)`, `where('assignedTo'==…)`, which use automatic single-field indexes. The one `collectionGroup('users')` query (login fallback) needs a collection-group single-field index on `users.email` — that is **not** listed here; if the fallback fails with "index required" this is why.

## 11. Key business logic

**Check-in / check-out** (`home_tab` is dead; the live path is `attendance_overview_tab` → `FirestoreService.recordAttendancePunch`):
1. Get GPS (accuracy filter, 30 s cache fallback), compute distance to `officeLat/Lng`.
2. If `hasPermission('geofencing')` the user must be within `allowedRadius`; otherwise the check is skipped.
3. Late check = `now > shiftStart + gracePeriod` (shift from the user's shift doc, else org defaults 09:00/18:00/15 min).
4. Three writes: user daily doc → company roll-up doc → user profile live status (`attendanceStatus`, `lastCheckIn/Out`).
5. Check-out computes `hoursWorked`/`hoursNum` from the stored check-in.

**Leave:** `apply_leave_screen` → `submitLeaveRequest` (double write) → `NotificationHelper` to managers/admins → approvers update status → employee is notified. The paid-leave quota is `paidLeavesPerYear` (default 12).

**Notifications** are always a pair: Firestore doc (in-app list + foreground listener) + OneSignal push (background).

**Multi-tenant guard:** every list that comes from a company-wide stream is run through `isDocInCurrentCompany`.

## 13. Problems found in the code

Ordered by severity. File links are relative to the project root.

1. **Silent data deletion of tasks** — [tasks_tab_view.dart:154](lib/widgets/tasks_tab_view.dart#L154) calls `doc.reference.delete()` inside `build()` for any task whose title is one of 8 hard-coded demo titles ("Review Q3 Policy Updates", "Generate Payroll Report", …). A real task with one of these names is deleted from Firestore the moment the Tasks tab opens, and the delete repeats on every rebuild. (This file **is live**.)
2. **Employee passwords sent in plain text by email** — [add_employee_screen.dart](lib/features/employee_management/screens/manager/add_employee_screen.dart) emails the new employee's chosen password through EmailJS. The EmailJS service/template/public key are hard-coded in client code, so anyone who unpacks the app can send mail through the account.
3. **OneSignal push is sent from the client** with a REST API key supplied by `--dart-define`. A key compiled into an app can be extracted and used to push to all users. Push should be sent from a backend / Cloud Function. Without the define the key is empty and pushes fail silently.
4. **Rules vs. code gaps** (section 8): `shift_requests`, `department_requests`, `task_requests`, announcement `comments`, company `overtime_requests` have no rule; `tasks` are writable by any member; `users/{email}` role/status can be edited by the owner; `audit_logs` open to all signed-in users; any signed-in user may create an `organizations` doc.
5. **Sensitive personal data**: Aadhaar number, blood group, address and emergency phone stored un-encrypted in the profile doc that every org member can read.
6. **Leave status casing**: submit writes `Pending`, review writes `approved`/`rejected`. At least one screen counts pending with an exact `== 'pending'` ([universal_leave_tab.dart:463](lib/features/leave_management/screens/shared/universal_leave_tab.dart#L463)) — verify the pending badge is correct.
7. **Leave approval updates one copy only** — [leave_approval_screen.dart:387](lib/features/leave_management/screens/manager/leave_approval_screen.dart#L387) updates the doc it was opened from. Because leave exists in two places (company queue and user sub-collection), the other copy can stay `Pending` forever unless the opened doc is also mirrored elsewhere.
8. **`date` field has two types** for the same attendance doc (string vs Timestamp), see 7.5. Queries on `date` can silently miss documents.
9. **Compile errors in dead files** (will break the build if anyone re-links them): `screens/employee/announcement_tab.dart` (missing imports for `FirebaseAuth`/`AppSession`), `screens/register_screen.dart` (imports `organization_setup_screen.dart`, which does not exist). `flutter analyze` is likely to report them.
10. **Hard-coded values**: document size `"1.0 MB"`, file name always `<title>.pdf`, office radius default 500 m, OneSignal app id, `Origin: http://localhost` header in EmailJS call.
11. **`.firebaserc` is empty** — `firebase deploy` will not know the project; run `firebase use attendence-a56dd`.
12. **No automated tests** — `test/widget_test.dart` has the body commented out.
13. **Settings stored in the notifications collection** (`notifications/settings|privacy|security`) are returned by any "all notifications" query. `notifications_screen.dart` has a "clear all" batch delete over that collection, which would probably remove those settings docs too (I did not trace it fully — worth testing).
14. **Performance**: nearly every screen opens a stream on an *entire* collection (`.snapshots()` with no `where`/`limit`) and filters in memory — e.g. all attendance docs for the company. This is slow and expensive (reads are billed per document) as data grows. Add `where('date', …)`/`limit` and use the indexes in section 9.
15. `unified_dashboard_screen.dart` is a 4,574-line file; `home_tab.dart` (dead) 2,431; `manager_home_tab.dart` (dead) 2,066 — hard to maintain.
